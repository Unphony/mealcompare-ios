用户已确认 0.1.2 当前功能，继续授权尝试自动选规格、用券与凑单。日常仍由 iPhone 本机运行，新增费用为 0；不提交订单或支付。创建和合并 PR 仍须分别确认。

## 缩小范围

按用户补充，利用历史订单和买过的套餐建立本机常买索引，优先按已知门店名、餐品名和规格查询。两条初始样例标为“用户指定”，不伪装成导入的订单。历史价格、红包资格、库存与送达时间不作为当前事实复用。

第一版历史导入只支持已核实的淘宝闪购当前订单列表中明确完成、单商品且数量明确为一件的摘要，最多二十条。多商品订单在该列表可能只有图片，没有可完整恢复的名称、数量与规格，应跳过；套餐摘要也不等于全部子商品规格已核实。美团历史页未核实结构，明确不支持。仅存门店、餐品、规格与数量，不读取付款金额、订单号、地址、电话或账号。

## 本轮实现范围

- 在当前已打开的门店页定位唯一精确商品，单次加购后读取购物车验证。菜单汇总数量不能证明某个具体规格的数量。
- 按组选择可用规格；淘宝闪购多子商品套餐须逐个切换、核对全部子商品后才确认。未知组合结构、同名歧义或缺货会停止，避免猜选。
- 只操作已有可用券。已兑换会员券可选择；未兑换会员权益不自动兑换或购买。美团现代 MachPro 券页尚未适配，保留平台默认用券报价并标明未遍历。
- 生成有界凑单购物篮，原价超过预算仍保留试价机会，最终按真实结算金额过滤。商品原价和观察到的优惠门槛仅用于排序，不能自行推算个人优惠后的应付额。
- 当前可见菜单并非完整目录，只有名称、规格能力和价格信息明确的附加品才可自动尝试。默认最多八个购物篮、每篮最多六个默认或已有券方案；限制和缺失目录均不能伪装成全局最优。
- 查询在前台执行。返回、首页、刷新或停止将取消旧任务；取消时可能停留在试验购物车，应在界面明确提示。不会为了恢复购物车而继续执行已经取消的动作。

本轮是当前门店内的操作链验证，仍需要用户进入目标门店。历史索引有助于后续自动识别和进入常买门店，不代表已完成跨平台同一实体店、同一完整规格和同地址的自动证明。

## 主要技术难点

1. **同一商品的身份**：平台名称、促销前缀、套餐子项不同；没有完整规格时，名称近似不能当作同餐。
2. **动态规格状态**：子商品、口味、份量、互斥与售罄会改变可选项。必须逐步观察结果，不能连续盲点。
3. **优惠相互影响**：面额最大的券不保证实付最低，满减、包装费、配送费及券互斥需由结算服务端重新计算。
4. **购物车与价格同步**：加购可能按起购数量增加多件，切券后可能仍显示旧金额。需验证实际车行、等待新结算内容稳定。
5. **有限候选的完整性**：历史记录能减少搜索范围；漏项、查询上限和未适配券类型仍须明确记录。
6. **维护网页适配**：两平台会更新页面或分流到不同版本；未命中已核实结构时停止，不退化成泛化点击。
